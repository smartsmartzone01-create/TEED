# Backend Database and Data Integrity

## Database standard

PostgreSQL is the production database. Django's ORM is the default persistence
interface. Raw SQL requires a demonstrated need, parameterized queries, tests,
and review.

## Shared model foundation

Persistent TEED models normally compose:

- `UUIDMixin`;
- `TimestampMixin`;
- `SoftDeleteMixin`.

`BaseModel` exposes these shared behaviors without adding business fields.

### UUIDs

- Primary keys use UUID version 4.
- UUIDs are generated by the application and are not editable.
- Public contracts serialize UUIDs as strings.
- Code must not infer ordering or business meaning from a UUID.

### Timestamps

- `created_at` records creation.
- `updated_at` records the latest saved change.
- Values are timezone-aware and stored in UTC.
- Application display may localize timestamps without changing stored values.

### Soft deletion

- `is_deleted` and `deleted_at` represent logical deletion.
- instance `delete()` soft-deletes by default;
- `restore()` reverses soft deletion;
- `hard_delete()` performs irreversible deletion explicitly;
- `objects` excludes deleted rows;
- `all_objects` includes all rows.

Queryset bulk operations must preserve the same meaning. Uniqueness rules must
be evaluated carefully when deleted rows remain in the database.

## Identity data

The current identity model supports:

- email;
- username;
- phone number;
- country code;
- verification flags;
- onboarding completion;
- staff and active state;
- Django permissions.

Email and username use case-insensitive database uniqueness constraints when
present. Phone numbers are normalized before persistence. Optional identity
fields use `NULL` only where absence is meaningful.

## Verification challenges

An email verification challenge stores:

- owning user;
- purpose;
- password-hashed code digest;
- expiry;
- attempt count and limit;
- consumption timestamp;
- base-model lifecycle fields.

Plain codes must never be stored. A database check constraint prevents
`attempt_count` from exceeding `max_attempts`.

The final hardened workflow must prevent concurrent requests from:

- consuming one challenge more than once;
- incrementing attempts beyond the limit;
- issuing tokens multiple times from one code;
- leaving multiple active challenges for one user and purpose.

Row locking or an equivalent atomic database strategy should protect those
transitions.

## Constraints

Use database constraints for invariants that must hold regardless of client:

- primary and foreign keys;
- business-required uniqueness;
- bounded numeric values;
- valid simple relationships between fields.

Complex workflows remain in services. Serializer validation alone is not a
substitute for database integrity.

## Transactions

Services own transaction boundaries. Use transactions when a workflow must
succeed or fail as one unit.

Do not keep a database transaction open during slow network operations. For
email and other external effects, persist state first and schedule delivery
after commit. Design retry and idempotency behavior explicitly.

## Query ownership

- selectors own reusable reads;
- repositories own persistence and reusable writes;
- services decide why and when operations happen.

Selectors should prevent N+1 queries using `select_related` or
`prefetch_related` when justified by measured access patterns.

## Migrations

- Generate migrations from model changes.
- Review the generated operations.
- Never edit an applied migration to represent a later change.
- Keep schema and data migrations focused.
- Plan safe roll-forward and rollback behavior.
- Test new databases and upgrades from supported existing states.
- Run `makemigrations --check` in continuous integration.

## Indexing

Indexes must correspond to real query and ordering patterns. Foreign keys and
uniqueness constraints create many necessary indexes automatically. Add
composite or partial indexes only with an identified query and verify their
cost on writes and storage.

## Testing requirements

Test:

- manager visibility for deleted rows;
- soft delete, restore, and hard delete;
- model properties and constraints;
- case-insensitive identity uniqueness;
- normalization;
- transaction rollback;
- concurrent verification transitions;
- selector and repository behavior;
- migrations where data transformation is involved.
